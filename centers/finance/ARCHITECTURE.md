# معماری شبکه مراکز خدمات مالی پورتال ورزش

## اصل طراحی
هر فدراسیون یک فضای کاری و پرونده داده مستقل دارد. همه مراکز از مدل داده، شناسه‌گذاری، قواعد مالی، قالب گزارش و نسخه ساختار مشترک استفاده می‌کنند. استقلال داده‌ای فدراسیون‌ها باید در سطح ذخیره‌سازی و مجوزهای سرور نیز اعمال شود؛ تفکیک ظاهری صفحه کافی نیست.

## اجزای معماری
1. **Federation Workspace**: برنامه اختصاصی هر فدراسیون، مانند `squash/`.
2. **Shared Finance Core**: قواعد مشترک برای تراکنش، بودجه، تعهد، سند، دوره مالی و گزارش.
3. **Storage Adapter**: اتصال هسته به ذخیره محلی، فایل، دیتابیس محلی یا API سرور.
4. **Central Aggregator**: دریافت بسته‌های استاندارد از فدراسیون‌ها و ساخت گزارش کلان بدون دسترسی خزانه‌دارها به پرونده سایر فدراسیون‌ها.
5. **Identity & Access**: احراز هویت، نقش خزانه‌دار، مدیر مالی و مدیر مرکزی؛ این بخش فقط در سمت سرور قابل اتکا است.

## شناسه‌ها و قالب تبادل
- `federationId`: شناسه ثابت و یکتای فدراسیون، مانند `FED-SQUASH`.
- `schemaVersion`: نسخه ساختار داده.
- هر رکورد: شناسه یکتا، شناسه فدراسیون، تاریخ، مبلغ عددی، شرح، زمان ایجاد و در صورت نیاز وضعیت تأیید.
- بسته JSON شامل آرایه‌های `transactions`, `budgets`, `documents` است.
- CSV جداگانه برای هر جدول، با شناسه‌های ثابت، امکان انتقال به Excel و Access را فراهم می‌کند.

## مسیرهای ذخیره‌سازی قابل پشتیبانی
| روش | پیاده‌سازی پیشنهادی | نکته |
|---|---|---|
| مرورگر محلی | LocalStorage برای نمونه سبک؛ IndexedDB برای داده و فایل بیشتر | مناسب پایلوت و کار تک‌دستگاهی |
| فایل‌های تبادلی | JSON کامل و CSV جدولی | مناسب پشتیبان و انتقال به Excel/Access |
| Microsoft Access | جداول رابطه‌ای با کلید اصلی/خارجی و فرم/گزارش | از طریق CSV یا واردسازی کنترل‌شده |
| دیتابیس محلی | SQLite به همراه برنامه محلی یا سرویس داخلی | مناسب یک رایانه یا شبکه داخلی |
| هاست آنلاین | API + PostgreSQL/MariaDB و ذخیره امن فایل | مناسب دسترسی چندکاربره و داشبورد مرکزی |
| شبکه داخلی آفلاین | سرور محلی + دیتابیس + رابط وب روی LAN | بدون نیاز به اینترنت |
| ترکیبی آفلاین/آنلاین | صف تغییرات، شناسه عملیات، نسخه رکورد و همگام‌سازی | نیازمند حل تعارض و ثبت لاگ همگام‌سازی |

## سیاست همگام‌سازی
- هر مرکز فدراسیون مالک داده عملیاتی خودش است.
- داشبورد مرکزی فقط داده‌های موردنیاز گزارش‌گیری را از طریق بسته امضاشده یا API مجاز دریافت می‌کند.
- در حالت آفلاین، تغییرات در صف محلی می‌مانند و پس از اتصال ارسال می‌شوند.
- برای جلوگیری از تکرار، هر رکورد شناسه یکتا و هر تغییر شناسه عملیات دارد.
- تعارض‌ها نباید بی‌صدا بازنویسی شوند؛ باید در صف بررسی و حل تعارض قرار گیرند.
- گزارش‌های مرکزی باید زمان آخرین همگام‌سازی و کامل‌بودن داده را نمایش دهند.

## امنیت و کنترل دسترسی
- نقش خزانه‌دار فقط به شناسه فدراسیون خودش محدود می‌شود.
- مدیر مرکزی مجوز گزارش‌گیری تجمیعی و دسترسی مدیریتی مشخص دارد.
- کنترل دسترسی در API و دیتابیس انجام می‌شود، نه با مخفی‌کردن دکمه یا انتخاب نقش در JavaScript.
- ارتباط شبکه‌ای باید TLS داشته باشد؛ عملیات مالی باید audit log تغییرناپذیر، پشتیبان‌گیری و کنترل تأیید داشته باشند.
- اطلاعات بانکی، شناسه‌های حساس و اسناد محرمانه نباید در مخزن عمومی Git یا فایل‌های نمونه قرار بگیرند.

## پایلوت اسکواش
پوشه `squash/` اولین پیاده‌سازی مستقل است. داده‌ها در کلید محلی مجزا ذخیره می‌شوند و خروجی JSON/CSV دارند. اگر مرکز و داشبورد روی یک مبدأ (origin) در یک مرورگر باز شوند، داشبورد مرکزی بسته محلی اسکواش را می‌خواند؛ برای دستگاه دیگر، فایل JSON را از بخش «ساختار فدراسیون‌ها» وارد کنید.

## مرحله بعد
1. نهایی‌سازی سرفصل‌های حسابداری و مراکز هزینه با خزانه‌دار فدراسیون اسکواش.
2. تعریف فرم‌های درخواست پرداخت، تنخواه، قرارداد، درآمد، اسناد و تأیید.
3. افزودن دفتر کل/معین و کدینگ حساب‌ها در صورت نیاز عملیاتی.
4. پیاده‌سازی SQLite یا PostgreSQL پس از تثبیت مدل داده.
5. راه‌اندازی احراز هویت و نقش‌ها و سپس اتصال فدراسیون‌های بعدی.
